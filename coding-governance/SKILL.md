# 编码治理

## 前置架构决策

本 skill 不自行决定模块职责、依赖方向、公开 API、共享状态或适配边界。如果任务触及任一项，先使用 `$architecture-governance` 建立或审计这些决策，再使用本 skill 实现其中的源码。不得在编码规范中临时虚构或覆写架构决策。

## 命名与结构

- 目录、文件、类/结构体、函数和变量的命名应清楚表达其责任，便于全局搜索、定位和追溯。遵循项目已定义的命名、类型、错误处理和格式化约定。
- 保持结构一致性：同类文件、同类代码单元和同类错误路径使用同一清晰模式，除非存在书面说明的差异。
- 文件大小和数量不是质量指标。保持职责聚合；只在可读性、独立测试或独立变更边界需要时拆分。

## 可读性与重复

- 代码应能被局部阅读：优先使用直接的控制流、明确的数据流和紧邻的错误处理。注释只解释不明显的原因或约束，不重复代码字面含义。
- 避免无意义的复制粘贴。当两处代码共享稳定责任且一处修复必须同时修复另一处时，提取合适的共同实现。当它们的变更速度或可读性需求不同时，保留独立实现并让差异可见。
